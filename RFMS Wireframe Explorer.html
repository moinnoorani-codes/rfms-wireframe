Scope switching rules

Built from the hierarchy you described: Trust Owner, then Trusts with Trust Managers, then Branches with Branch Managers. A person logs in once. What they see, and where they can switch to, comes only from where they are assigned.

1. Who lands where

Nobody sees the names or number of trusts and branches outside their access. Only the Trust Owner and a Trust Manager of 2 or more trusts get a combined view.

2. How switching works

1

One person, one login

The mobile number identifies the person across the organisation. Roles attach to a level (organisation, trust or branch), not to the login. Switching never asks for the password again.

2

Open straight into the work

Owner: all trusts. Trust Manager: all branches of the trust. One branch: that branch. One module: that module's screen. No in-between screen listing what exists.

3

Show nothing above their level

The breadcrumb starts at the person's own top level. A Trust Manager never sees the organisation name or how many other trusts exist. A Branch Manager never sees the trust's other branches.

4

Every scope has its own address

Example: /o/srcf/t/srmt/b/mm/dashboard. Links can be bookmarked or shared. The server checks access on every request. A link outside your access shows No access, never data.

5

The menu is rebuilt on every switch

It comes from three things: the role held at this level, the modules switched on at this branch, and any per-person overrides. A hidden item means no access, not read-only.

6

Overviews are for reading and approving

Tickets, receipts, bookings, stock and attendance are entered at a branch. Add donation on an overview first asks which branch, listing only branches where the person can create donations.

7

Combined figures never exceed access

A Trust Manager of 2 trusts sees the sum of those 2 trusts only. Organisation totals are for the Trust Owner alone.

8

Approvals flow up

A receipt edit after the 10-minute window goes to the Trust Managers of that trust and to the Trust Owner. Pending approvals show on every overview that covers that branch.

9

Switch only when there is somewhere to go

The switcher appears only for people with access in more than one place, and lists only those places. Single-place users get a plain label. Recent keeps the last 3 places.

3. Decisions to confirm before build

Found while checking this design against PRD v1.1 and the wireframe brief.

A

3 levels or 4?

PRD v1.1 describes Organisation, Trust, Location, Unit and says there is no Branch level. Your DB schema and this design use Trust Owner, Trust, Branch.

Recommendation: Update the PRD to 3 levels. Branch replaces Location. Units become modules or counters inside a branch, not a level.

B

Receipt numbering

PRD v1.1 says one serial per trust. The wireframe brief says one per branch.

Recommendation: One series per branch with trust and branch codes in front: SRMT-MM/26-27/1874. Unique inside the trust and keeps working when a branch is offline. Offered as a choice on Trust registration.

C

Login flow and user records

The brief has mobile, then pick a branch, then password. With the switcher it becomes mobile, password, home scope.

Recommendation: One user record per person plus a separate assignments table, instead of one user row per branch. Existing TTFMS users need merging by mobile during migration.

D

Hosting level

The brief puts SaaS or self-hosted on each branch. Combined dashboards can only include a self-hosted branch after it syncs.

Recommendation: Choose hosting once per organisation in v1. If mixed hosting is needed later, show the last sync time on that branch's figures.

E

Who creates what

Assumed in these wireframes: only the Trust Owner creates trusts and Trust Managers. Trust Managers create branches and branch staff when given Branches: Create.

Recommendation: Confirm, or limit branch creation to the Trust Owner.

F

Trusts with one branch

Gaushala Charitable Trust has 1 branch. Assumed: its manager still lands on the trust overview, because approvals, 80G and trust reports live there.

Recommendation: Keep as assumed. The alternative is to skip straight to the branch, which hides trust-level items one more click away.

4. Data shape this needs

Replaces a user row per branch. TrustOwner, Trust and Branch tables stay as they are.

TableColumnsWhy
usersid, mobile (unique), name, email, password_hash, statusOne row per person, whatever they manage
user_assignmentsuser_id, scope_type (OWNER, TRUST, BRANCH), scope_id, role_id, statusA person can hold several assignments at different levels
assignment_permissionsassignment_id, module, can_create, can_read, can_update, can_deletePer-person overrides on top of the role defaults
branches.enabled_moduleslist of modules switched on at the branchDrives the branch menu and quick actions

5. Not recommended

  • Greyed-out trusts or branches the person cannot openIt reveals that they exist and creates support calls. Hide them.
  • Entering receipts at trust or organisation levelA receipt needs a branch for its number, printer and stock. The overview asks for a branch first.
  • A token that lists every trust and branchFor an Owner with many branches the token grows large and goes stale when access changes. Keep the token to user and organisation, and resolve assignments on the server per request, with a short cache.
  • Showing names or access before the passwordThe earlier brief listed every trust and branch after only the mobile number. Anyone could type a number and see them. Nothing is shown now until the password is correct.
B1Login. The branch selection step from the earlier wireframe brief is removed. Choosing where to go now happens inside the app, with the scope switcher.
